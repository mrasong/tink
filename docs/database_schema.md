# Tink Database Storage Layout

[English](database_schema.md) | [简体中文](database_schema.zh-CN.md)

> **Version**: v0.9.30

The Tink server persists everything in an embedded **bbolt** key-value database — a single file `<data>/tink.db` (mode `0600`, open timeout 3 s). The design combines prefix-ordered binary indexes with O(1) hash lookups. There is no external database.

Boolean conventions differ by layer: entities stored in buckets use `uint8` `0/1` (`SecretKey.enabled`), `meta` values are plain strings (`"true"`/`"false"`), and the Settings API exchanges real JSON booleans.

---

## 1. Bucket Overview

The flat Secret-Key architecture removed the legacy `users` entity: Secret Keys and Devices are the core entities. All 9 buckets are created at open:

```text
tink.db
├── Core data buckets
│   ├── secret_keys           # Auth key entities (indexed by key ID)
│   ├── sk_hashes             # SHA-256 hash side-index → key ID (O(1) auth lookup)
│   ├── devices               # Client devices (bound directly to key_id)
│   ├── messages              # Notifications (auto-increment uint64, big-endian keys)
│   ├── sessions              # Browser session tokens (cookie auth)
│   └── meta                  # Flat global settings (bark_relay_enabled, …)
└── Secondary ordered indexes (range scans)
    ├── idx_key_messages      # key_id:message_id timeline   (write-only today)
    ├── idx_device_messages   # device_id:message_id timeline (drives SSE replay)
    └── idx_group_messages    # group:message_id timeline    (write-only today)
```

## 2. Core Buckets

### 2.1 `secret_keys`

- **Key**: `key_id` (`string`, e.g. `"admin"` or `"sk_3WHyWNzJ"`)
- **Value**: JSON `SecretKey` entity

```json
{
  "id": "sk_3WHyWNzJ",
  "name": "GitHub Actions CI",
  "role": "user",
  "hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "enabled": 1,
  "created_at": 1789258500000,
  "last_used": 1789258800000
}
```

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Key ID (`admin`, or `sk_` + last 8 chars of the raw token) |
| `name` | `string` | Free-form label ("Grafana", "Work Mac", …) |
| `role` | `string` | `"admin"` (protected: cannot be disabled/deleted) or `"user"` |
| `hash` | `string` | SHA-256 hex of the raw secret — plaintext is never stored |
| `enabled` | `uint8` | `1` active / `0` disabled (disabled keys are rejected at auth) |
| `created_at` | `int64` ms | Creation time |
| `last_used` | `int64` ms | Last successful API call (omitted when `0`) |

`GetKeyByHash` refreshes `last_used` on every authenticated request and lazily migrates legacy rows that were keyed by hash.

### 2.2 `sk_hashes`

- **Key**: SHA-256 hex of the raw token
- **Value**: `key_id` (`string`)

A Bearer token arrives → hash it → O(1) lookup here → load the entity from `secret_keys`. No full scans on the auth path. Written and deleted in the same bbolt transaction as `secret_keys`.

### 2.3 `devices`

- **Key**: `device_id` (`string`, persistent UUID generated by the macOS client)
- **Value**: JSON `Device` entity

```json
{
  "id": "dev-macbook-pro",
  "key_id": "sk_3WHyWNzJ",
  "name": "MacBook Pro 16\"",
  "created_at": 1789258530000,
  "last_connected_at": 1789258530000,
  "last_disconnected_at": 1789258800000
}
```

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Device UUID |
| `key_id` | `string` | Owning Secret Key (data isolation for user keys) |
| `name` | `string` | Friendly label |
| `created_at` | `int64` ms | First registration |
| `last_connected_at` | `int64` ms | Last SSE connect |
| `last_disconnected_at` | `int64` ms | Last SSE disconnect (`0` = never) |

Online status is never persisted: the API's `status` field is computed at runtime from the SSE Hub. Registration is an upsert that preserves the existing `key_id` binding and timestamps.

### 2.4 `messages`

- **Key**: 8-byte big-endian `Itob(message_id)` — the B+ tree therefore stores messages in strict chronological order
- **Value**: JSON `Message` entity

```json
{
  "id": 10024,
  "key_id": "sk_3WHyWNzJ",
  "devices": ["dev-macbook-pro"],
  "group": "deploy",
  "title": "Deploy succeeded",
  "body": "v1.2.0 is live and health checks passed",
  "url": "https://dashboard.example.com",
  "sound": "default",
  "payload": { "env": "production", "git_sha": "7abecb3" },
  "created_at": 1789258800000,
  "expires_at": 1789863600000
}
```

| Field | Type | Description |
|---|---|---|
| `id` | `uint64` | Globally monotonic sequence (`bbolt.NextSequence()`) |
| `key_id` | `string` | Sending Secret Key |
| `devices` | `[]string` | Target device IDs — only pushes with Tink targets are persisted; Bark-only pushes never touch this bucket |
| `group` | `string` | Notification group label (client-side aggregation) |
| `title` / `body` | `string` | Notification text |
| `url` | `string` | Click-through link |
| `sound` | `string` | Sound name (`default`, `glass`, `silent`, …) |
| `payload` | `object` | Arbitrary pass-through JSON |
| `created_at` | `int64` ms | Persist time |
| `expires_at` | `int64` ms | Retention cutoff, default `created_at + 7 days` |

### 2.5 `sessions`

Cookie-based browser sessions (`tink_session`), added with the dashboard login flow.

- **Key**: SHA-256 hex of the raw session token (a 64-hex random string issued at login)
- **Value**: JSON `Session` entity

```json
{
  "token_hash": "9a1f…",
  "key_id": "admin",
  "created_at": 1789258500000,
  "last_seen": 1789258800000,
  "absolute_exp": 1789272900000
}
```

Lifetime: **8 h idle** (tracked via `last_seen`, refreshed at most once per 60 s) and **24 h absolute** (`absolute_exp`). Expired sessions are deleted lazily on lookup and hourly by the background cleaner. Logout deletes the row immediately.

### 2.6 `meta`

Flat string key/value global settings (currently the Bark Relay trio):

| Key | Example | Description |
|---|---|---|
| `bark_relay_enabled` | `"true"` / `"false"` | Enables dual-push forwarding and the transparent proxy (reader also accepts `"1"`) |
| `bark_server_url` | `"https://api.day.app"` | Upstream Bark server (self-hosted supported); trailing `/` trimmed, empty falls back to `https://api.day.app` |
| `bark_route_path` | `"/bark-relay"` | Local proxy prefix used by the iOS Bark App; normalized to a leading `/` (empty or `/` → `/bark-relay`) |

Defaults: relay **disabled**, `https://api.day.app`, `/bark-relay`.

## 3. Secondary Index Buckets (offline replay & range scans)

Purpose: when a macOS client reconnects after sleep or an outage, the server replays missed notifications losslessly via `Last-Event-ID`.

### 3.1 `idx_device_messages` — the replay workhorse

- **Key**: `{device_id}:` + `Itob(message_id)` (last 8 bytes big-endian uint64)
- **Value**: `Itob(message_id)`
- **Read path**: cursor seeks to `{device_id}:{Itob(afterID+1)}` and scans forward under the prefix, filtering `now < expires_at` — O(log N + K). The SSE endpoint caps a replay at **200** messages. This is currently the only index with a read path.

### 3.2 `idx_key_messages` / 3.3 `idx_group_messages`

Same encoding with `{key_id}:` / `{group}:` prefixes. Written in the same transaction as the message; reserved for per-key auditing and per-group aggregation — **no query API reads them yet**.

## 4. Consistency & Automatic GC

### 4.1 Transactional invariants

- Key create/update/delete writes `secret_keys` and `sk_hashes` in one bbolt transaction — index and entity can never diverge.
- Message persist writes `messages` plus all three index buckets in one transaction.
- Device registration preserves the existing `key_id` binding on re-register, enforcing per-key isolation.

### 4.2 Background cleaner (hourly)

A server goroutine runs every hour (and at startup):

- Scans `messages`; when `now > expires_at`, cascade-deletes the record from `messages` and all index buckets.
- Sweeps expired rows from `sessions`.

This keeps the single bbolt file from bloating with dead notifications and stale sessions.
